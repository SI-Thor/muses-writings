## Part I — What the Repository Actually Contains

### The primitives, and what "the ledger drives the kernel" means

The system is a Rust workspace of roughly twenty crates under `crates/` — `octopus-runtime` (the kernel proper, ~174KB of source), `octopus-ledger`, `octopus-ledger-store`, `octopus-ledger-index`, `octopus-policy`, `octopus-ee`, `octopus-interfaces`, `octopus-interface-projection`, `octopus-interface-transport`, `octopus-app` (the daemon), `octopus-app-server`, `octopus-descriptors`, `octopus-file-storage`, `octopus-marks`, `octopus-run-record`, `octopus-schemas`, `octopus-tool-handlers`, `octopus-tool-registry`, `octopus-verifiers`, `octopus-worker-env`. Summing source and test bytes across those crates gives ~1.6MB of Rust, which at typical density lands at ~45,000 lines. **The headline claim is accurate, and conservative** — it counts only the kernel; the registry packages (one file, `octopus-process-session-tool-runtime/src/lib.rs`, is ~486KB alone) and the Electron client add far more.

The primitives, as documented in `docs/contracts/` and matched against crate names that implement them:

- **Interface** — a typed port between the system and the world. Its identity is *a folder path* in `registry/interface/`; there is no other identifier. Each interface is a live process that reads its own movements from the ledger: "the kernel never pushes anything and never decodes a payload." Telegram, Slack, IMAP/SMTP, cron, file-observation, a microphone, a speaker, web search, MCP stdio, and ~25 model providers (OpenAI, Anthropic, Gemini, DeepSeek, Ollama, vLLM, xAI, Zhipu, Kimi, MiniMax, Groq, Cerebras, Together, Mistral, OpenRouter, and more) all exist as folders in the tree. This is proven by inspection: handler/lifecycle code, `interface_state_db` SQLite files, `provider_ids.jsonl`, retry loops with exponential backoff, outgoing-delivery ledgers, dedup-at-birth logic, backpressure windows for synchronous tool calls, outbound parking with a 16KB minimum attachment size and a 7-day purge. These are the messy details of real integrations, not a diagram.
- **Artifact** — the only thing that crosses any boundary. A manifest names itself and points at a payload pinned by content hash. No runtime `kind`; what matters to the kernel is route, caller, movement.
- **Run and checkpoint** — a run is a durable execution *record*, not a process: no thread, no lease, no supervisor. A checkpoint parks a run on an interface; the run wakes when the awaited artifact lands. The `runs_wake_on` index and `run_record` crate back this. "Data, not a process" is implemented, not aspirational.
- **Worker** — a *description*, not a program: role plus a permission ceiling. In the registry the shipped pins (`coder`, `coder_max`, `planner`, `reviewer`, `computer_use`, `web`, `memory`, `sovereign`, …) are literally two JSON files each — an interface descriptor and a `policy.json` ceiling — hash-anchored, with the registry contract version committed in the tree.
- **Execution environment (EE)** — goal plus policy, nestable, with the rule that an inner environment is always strictly narrower. The root goal is `existence`. Multiple roots are supported via `bootstrap_root`.
- **Policy** — the most interesting primitive, and the one with a real contract (`docs/contracts/POLICY.md`). Policy is **never stored**. At every artifact arrival, a deterministic "formation" script recomputes the grant from pinned inputs: `grant = worker ceiling ∩ EE chain ∩ run bindings`. The bytes of every descriptor the formation read are retained in a content-addressed blob store, so a grant can be re-derived exactly, forever. Two rules matter enormously: *the creator is not an input* — capability is granted by where the run lives, never inherited from who spawned it — and "storage does not make a grant valid, it makes it invalid."
- **Mark** — the success tick. The runtime records a mark only after a verifier package passes. The verifier is itself just a removable folder in `registry/verifier/`, any language, stdin/stdout. Shipped verifiers include `artifact_exists`, `build_success`, `ocr_text_contains`, `operator_approval`, `review_rubric`, `tool_result_correspondence`, `review_rubric`, `memory_capture_outcome`. There is **no mark-emission tool anywhere in the tool registry** — I checked the tree; an agent cannot claim success, only have success recorded for it.

"The ledger drives the kernel" concretely means: `ledger/movements.jsonl` is an append-only, source-of-truth event log; `ledger/blobs/` holds content-addressed manifests; `ledger/ledger-index.sqlite` is a *disposable* index; and an in-memory index provides idempotency. A refusal is a row too — typed (`DeliveryRefused`, `VerificationFailed`, `turn.error`), never a silent drop. Restart recovery is deliberately absent as a subsystem: everything is data on disk, so the runtime rescans movements, wakes interfaces, and each interface catches up from its own cursor. "Stopping and restarting the runtime is a path, not a signal."

### Self-modification, and what governs it

The scenarios doc describes an agent acquiring a camera capability: a run that can't see needs one → authors a run for a coder worker, with artifacts that run must prove → the coder writes the driver (`manifest.toml`, a Python lifecycle, a binding `project.json`) → an `ocr_text_contains` verifier checks behavior on a sample row → the interface folder appears in `registry/interface/` → the descriptor is picked up live → the parked run retries. The same mechanism covers the system editing its own client and autonomously renaming skills (a verified self-edit example in the tree). Two levels are distinguished honestly: descriptor-level extension (file edits under a grant) and source-level (editing the kernel itself through a granted git-worktree room, with branch isolation — `git_worktree` is a shipped worker-environment kind).

What governs it: the formation rule above, plus `operator_approval` — a verifier whose access tier binds a *task*, with a caret appearing in the effective policy. The approval surface is per-call: "Allow once / Decline," decided once, not a session, not a compiled rule.

### The five concepts, implemented

The architecture doc includes a mapping table that keeps the marketing honest: **Home** = one continuous run in the root EE; **Project** = an EE with its own goal and permissions; **Agent** = a reusable worker template (a `system_worker_*` pin plus authoring defaults — the "two JSON files" claim is literal); **Task** = a run (pausable/resumable *because* it is data that parks on checkpoints); **Driver** = a worker-environment kind (`filesystem_workspace`, `git_worktree`, `browser_session`, `container_session`, `desktop_session` via macOS accessibility/PIP, `process_session`, `remote_exec_server`, `mcp_stdio_session`, `code_mode`, `web_search`, `audio_device_session` — all present in the tree, plus pre-packaged client descriptors under `app/distribution/local-packages/`). The desktop client is an Electron app that is explicitly "a projection of runtime state," and Codex is ported as *one interface among many* — the security doc is blunt that there is no bundled model account: you sign into ChatGPT and Codex runs inside an interface.

### Maturity: grading the evidence

**Proven:** the code exists at the claimed scale and is internally consistent with the docs to a degree I did not expect. Tests are extensive — nearly every crate has an integration-test suite (`octopus-app-server/tests/` includes `worker_interface_cross_run_fan_out.rs`, `embedded_spine_drives_a_live_turn.rs`, an `architecture_dependency_guard.rs` that enforces the crate-dependency rules in CI, and even a `doomsday.rs`); the client has dozens of `test-*.cjs` scripts; there is a substantial `quality.yml` workflow. The registry is populated, not scaffolded.

**Claimed but unproven:** that the *scenarios* work. The repo says so itself: the scenarios "describe the intended use of the architecture, rather than tested, ready-to-use features." The README concedes the deeper point: "today's models — GPT-6 included — do not take initiative on their own, and for an ordinary coding task Octopus gives you nothing that Codex CLI does not already give you." Known gaps the authors list themselves: no schema migrations (contract changes reset your Home to a fresh one), no recovery subsystem, per-run depth is one provider.

**Grade:** a real architecture, really built, at research-preview maturity. Repository created **2026-10-09**, last push **2026-11-07** — one month old, one contributor (`miuuyy`), 734 stars and 80 forks riding the AlphaSignal spike, but **3 watchers and 1 open issue**: essentially no community yet, bus factor one, **zero published releases** (build from source, macOS only). A codebase of this size appearing in a month from one person implies heavy AI assistance — fitting, given the subject, and it cuts both ways: the consistency suggests disciplined generation, and nobody has audited any of it.

## Part II — The Comparison

| Octopus primitive | Our equivalent | Verdict |
|---|---|---|
| Append-only `movements.jsonl`; refusals are typed rows, never silent drops | agent-inbox ledger (tasks/claims/verdicts as git files) | **Same problem, different answer** — theirs is lower-level (events, not documents) and their refusal-typing is ahead of ours |
| Run/checkpoint: park-and-wake as data; no process, no lease | Muse durable goals, pausable tasks, crons/hooks | **They are ahead on mechanism** — resumability is a *consequence* of their data model; ours is a runtime feature we built |
| Policy formation: recomputed at every arrival from hash-pinned inputs; creator not an input | Jacquard charter-scoped auto-allow compiled from approval history; advisors never the gate | **Ahead on composition and replay**; **behind on the human** — they have no batching, no compiled history, per-call stalls |
| Marks: runtime-recorded success ticks after verifier packages; no mark-emission tool exists | Doctrine: verify effects in a store the actor cannot write; world-evidence verdicts (Minecraft triples library) | **Ahead in generality** (verifier as removable package); our "actor can't write the verdict store" separation is the stronger *trust* boundary — their verifier scripts run in the same trust domain |
| Worker = two JSON files (role + ceiling), hash-pinned | agent-inbox agent definitions; Muse declared briefs | **Same problem, different answer** — theirs is more radical (agent as pure description) and cleanly versioned |
| Interface identity = folder path; "the path is the permission" | Muse SSH seats with declared briefs | **Ahead on uniformity**; we're ahead on geography (multi-machine fleet is measured reality for us, a `remote_exec_server` package for them) |
| EE nesting, strictly narrowing; grant by place, not inheritance | Jacquard charter scopes; shared-state claim protocol after lane collisions | **Ahead conceptually, unproven at scale** — we have a year of fleet ops; their nesting has CI tests, not fleet history |
| Everything (tool/verifier/mark/artifact) is a registry folder; "if adding X requires touching app bootstrap, a primitive has leaked" | Skills + MCP + bespoke triples | **Ahead on internal uniformity, behind on ecosystem** — MCP already won the interop war they're fighting with folders |
| Per-call Allow-once/Decline approvals binding task access tier | Jacquard batched operator queue; hash-bound proposals; queued ≠ rejected | **Behind** — this is the mistake we already made and measured |
| Single-root local system, Home resets on contract change, zero releases, bus factor one | Year-scale persistent state across machines; Jacquard v1.3.0 | **Solving a problem we don't have** (and refusing one we've already solved) |

**Where they are genuinely ahead of us.** Three places. First, *refusals as typed ledger rows* — in agent-inbox, a rejected or malformed claim is a file state; in Octopus it is a first-class event with a type, which makes "why did nothing happen" answerable by querying the log. Second, *formed-not-stored policy* — Jacquard's auto-allow rules are compiled artifacts that can drift from their inputs; Octopus's grants are pure functions of hash-pinned inputs, recomputed on every arrival, which makes every historical decision exactly re-derivable. We should be honest that this is a better mechanism than ours even though we have the better *process* around it. Third, *the mark contract* — we have measured "claimed-but-not-done" as our recurring failure class, and our answer has been doctrine plus external verdict stores. Their answer is structural: success simply cannot be self-reported. That's the strongest idea in the repo.

**Where they are repeating mistakes we already made and measured.** The approval model is the obvious one: per-call, synchronous, Allow-once/Decline, decided in the client. This session is a live counterexample running in their own shop — my `Bash` and `WebFetch` lanes are Jacquard-queued right now, five proposals deep, and the work survived only because an ungoverned reader path existed. Jacquard batches decisions and compiles history into charters *because* per-call gating stalls lanes; Octopus's `operator_approval` verifier will stall every governed run on a human, and its capability ceiling ("Access tiers clamp capabilities; more capable does not mean more powerful") is exactly the policy that made our executors systematically weaker than their tasks required until we measured delegation depth. Their persistence posture is the second: no schema migrations, Home resets on contract change, no recovery subsystem. That is a perfectly rational choice for a one-month research preview — and ruinous at the year scale our Muse seats and world state operate on.

**Where it's the same problem with a different answer.** Their ledger answers our inbox with events instead of documents — movements versus tasks/claims/verdicts. Ours is human-reviewable in place (it's a repo); theirs is replayable by construction (it's an event log with disposable indexes). Their knowledge story — memory workers (`memory`, `memory_consolidation`, `memory_observer` pins with `memory_capture_outcome` verifiers) — is the same shape as our citizens' externalized triples library, but theirs is generic while ours carries world-evidence verdicts, which is the part that made externalization worth doing.

## Part III — Steal / Don't Steal / Open Question

**Three things to steal.**

1. **Typed refusals as ledger rows.** "A refusal is a row too — typed, never a silent drop" costs almost nothing in agent-inbox (a refused claim becomes a typed verdict event with machine-readable reason) and directly attacks our debugging tail. We already learned this lesson once with the shared-state claim protocol: collisions were invisible until they were recorded.
2. **Formed, never stored, policy.** Re-express Jacquard's auto-allow rules as pure formation functions over hash-pinned inputs (charter, scope, actor pin), recomputed at evaluation time, with the input bytes retained in content-addressed storage. Every approval in history becomes exactly re-derivable, and "storage does not make a grant valid, it makes it invalid" becomes a lint rule for our compiled charters.
3. **Non-emittable marks.** Move success-recording out of the tool surface entirely: no agent-callable "record success" path, only the runtime (or a store the actor cannot write) recording a mark after a verifier passes. Our citizens' verdict triples already point there; Octopus proves it can be a *general* runtime contract rather than a per-world convention.

**Two things not to steal, with the measured reason.**

1. **Per-call synchronous operator approval.** We ran per-call gates; lanes stalled on humans; Jacquard's batching and charter compilation exist as the measured fix. Octopus's Allow-once/Decline binding a task's access tier re-introduces the stall at the exact point our year of data says it hurts most — the moment an agent is mid-delegation.
2. **The persistence posture: no migrations, Home resets, rescan-as-recovery.** Rational at one month and one user; our Muse seats, cron state, and Minecraft world carry months of accumulated history across machines. A contract change that resets state would erase exactly the long-running evidence our architecture exists to accumulate. (Their honesty about it — "we do not write migration code" — is worth copying even as we reject the policy.)

**One question their design raises that we haven't answered.** Octopus's rule that *the creator is not an input* — capability granted by place, never inherited — deliberately allows a low-capability orchestrator to spawn a *higher*-capability executor inside a strictly narrower environment. Our agent-inbox claim protocol implicitly does the opposite: a claim inherits the claimer's lane scope, so delegation can only ever be as powerful as the delegator. That choice was made to stop lanes colliding on live state, and it worked — but Octopus forces the question: **when a weak planner meets a task that needs a strong executor, does our claim inheritance systematically under-power the executor, and can a Jacquard charter admit a delegate *more* capable than its delegator without handing it the keys to the whole lane?** We have no measured answer. They at least have a formation rule that makes the question precise.
